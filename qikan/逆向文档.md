# 维普期刊 — 逆向全链路分析

## 1. 目标

| 项 | 内容 |
|----|------|
| URL | `https://qikan.cqvip.com/Qikan/Journal/JournalGuid?from=index` |
| 目的 | 绕过 RS6 反爬，获取期刊导航真实页面 HTML |

## 2. 请求链路总览

```
浏览器访问 qikan.cqvip.com
  → 服务端检测到无合法 Cookie
  → 返回 412 + $_ts JS 挑战页（3KB）
  → 浏览器执行 $_ts VM 字节码（226KB 外部 JS）
  → VM 从 meta/nsd/cd 提取数据 → 计算合法 Cookie
  → Set-Cookie: S Cookie（服务端）+ T Cookie（客户端生成）
  → 二次请求（带 S+T Cookie 对）
  → 200 真实页面
```

## 3. 防护识别

### 3.1 最初发现

```
$ curl https://qikan.cqvip.com/Qikan/Journal/JournalGuid?from=index
→ HTTP 412 Precondition Failed
→ Body: 3KB HTML，含 <script r='m'>$_ts=window['$_ts']...</script>
→ Set-Cookie: 6HZbKHDjIEcgS=60t_... (动态名/值，每次不同，HttpOnly)
```

### 3.2 识别为瑞数 RS6

关键特征：

| 特征 | 值 | 意义 |
|------|-----|------|
| `$_ts` 全局对象 | `$_ts.nsd`, `$_ts.cd` | 瑞数 VM 入口 |
| `r='m'` 属性 | 出现在 script 和 meta 标签 | 混淆标记 |
| 服务器头 | `Tengine/3.1.0` | 阿里 Tengine |
| 外部 JS | 226KB `/Qikan/Scripts/rs/xxx.js` | RS VM 字节码 |
| Meta 签名 | `<meta id="FbkwzLN5XOx0" content="..." r='m'>` | 签名载荷 |

### 3.3 排除 TLS 指纹

```python
# 测试 1: plain requests
requests.get(url) → 412

# 测试 2: curl-cffi (Chrome120 指纹模拟)
curl_cffi.get(url, impersonate="chrome120") → 412

# 结论: TLS 指纹不是主因，412 来自 JS 执行缺失
```

## 4. 412 挑战流程

### 4.1 首次请求 → 412 响应

服务端返回的 JS 挑战页结构：

```html
<html>
  <meta id="FbkwzLN5XOx0" content="eyJiYWJ5Ijp..." r='m'>  <!-- 混淆签名 -->
  <script r='m'>
    $_ts = window['$_ts'];
    $_ts.nsd = 52203;
    $_ts.cd = "qxrErrAl..."  // ← 核心载荷，三层嵌套 VM 字节码
  </script>
  <script src="/Qikan/Scripts/rs/xxx.js" r='m'>  // ← 226KB VM 解释器
</html>
```

### 4.2 浏览器执行流程

```
1. 加载外部 226KB VM 解释器 JS
2. 读取 meta 签名 + $_ts.nsd + $_ts.cd
3. VM 执行三层嵌套字节码:
   L1: $_ts.cd 解码 → 中间代码
   L2: 中间代码执行 → 环境检测 (document.all, canvas.toDataURL, ...)
   L3: 环境通过 → 生成 T Cookie 值
4. JS 设置 document.cookie = S Cookie (服务端 Set-Cookie) + T Cookie (VM 生成)
5. 触发 sdenv:exit → 通知外部 Cookie 就绪
```

### 4.3 Cookie 结构

```
S Cookie: 6HZbKHDjIEcgS=60t_...  (服务端下发，HttpOnly，10 年过期)
T Cookie: 6HZbKHDjIEcgT=04CEW2P... (VM 生成，与 S 配对)
```

**S+T 必须配对**，服务端无状态校验：S Cookie 包含服务端密钥签名，T Cookie 是客户端 VM 执行结果，两者共同验证请求合法性。

## 5. 方案选择：路径 A vs 路径 B

### 路径 A：算法追踪（放弃）

试图从 `$_ts.cd` 中提取纯净算法：

- `$_ts.cd` 是三层嵌套 VM 字节码
- 每层使用不同的指令集和寄存器映射
- 环境检测代码与业务逻辑交织，无法单独剥离
- **耗时评估：> 2 周，且每次网站更新 VM 代码需重来**

### 路径 B：环境伪装（采用）

使用 sdenv（jsdom + 环境补丁 + VM 执行）自动完成 412 → Cookie 全过程：

```
jsdomFromUrl(url)
  ├─ jsdom 模拟 DOM（解析 HTML/script/meta）
  ├─ 环境补丁（canvas.toDataURL, document.all=undefined, ...）
  ├─ 加载外部 VM 解释器
  ├─ 执行 $_ts 挑战
  └─ sdenv:exit → Cookie 就绪
```

### 为什么 sdenv 能工作

RS6 的 VM 需要完整 DOM 环境（非纯算法），sdenv 提供了：
- jsdom：HTML 解析、script 执行、cookie 管理
- 环境属性补丁：canvas、navigator、document.all 等
- VM 解释器：完整执行 226KB 外部 JS

**关键要求：**
- Node.js ≥ v20.19.5（sdenv v1.1.3 依赖 undici ^7）
- VS 2022 Build Tools + C++ 桌面开发（编译 canvas/documentAll 等 C++ 原生模块）

## 7. 最终方案架构

```
Python(fetch_page.py)
  │
  ├─ subprocess.run(["node", "code/sdenv_rs6.js"])
  │     │
  │     └─ sdenv_rs6.js
  │           ├─ jsdomFromUrl(target_url)
  │           ├─ 等待 sdenv:exit (12s 超时)
  │           ├─ cookieJar.getCookieStringSync()
  │           └─ stdout → Cookie 字符串
  │
  ├─ 解析 Cookie → dict
  ├─ NODE_PATH=env/node_modules  ← 关键！
  │
  └─ requests.get(url, cookies=cookie_dict)
        └─ HTTP 200 → data/journal_guid.html
```

## 8. 关键踩坑记录

### 8.1 sdenv 原生模块编译

`pnpm install` 不会自动编译 sdenv 的 C++ 模块。`build/Release/documentAll.node` 需要 VS 2022 编译。解决：
- 方案 A：`pnpm rebuild sdenv`（需要 VS2022）
- 方案 B：从已有编译环境复制 `build/` 目录

### 8.2 Node.js 版本兼容

- v24：webidl-conversions crash（`ArrayBuffer.prototype.resizable` 未定义）
- v22：NODE_MODULE_VERSION 不匹配（需要重新编译）
- **最终使用 v24 + 从原始环境复制 build/**

### 8.3 NODE_PATH

Node 模块解析从 `code/sdenv_rs6.js` 所在目录向上查找，不会自动找到 `env/node_modules/`。必须在 subprocess 环境中设置 `NODE_PATH=env/node_modules`。
